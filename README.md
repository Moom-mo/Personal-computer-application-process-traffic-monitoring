# 个人电脑应用进程流量监控

基于 C/S 架构的进程网络流量监控助手。后台采集服务无界面、常驻运行，负责抓取
各进程的网络连接与流量增量并持久化到 SQLite；前台 GUI 完全独立，通过本地
TCP Socket 向服务端索取数据。两者可分别启动、分别退出。

## 环境要求

- Python 3.8+（开发环境为 3.12）
- Windows（采集层依赖 Windows 的进程 I/O 计数器语义）

```bash
pip install -r requirements.txt
```

## 运行

需要**两个终端**，先启动服务端再启动客户端：

```bash
# 终端 1：后台采集服务（无界面，Ctrl+C 退出）
python server.py

# 终端 2：前台监控界面
python client.py
```

首次启动会自动在项目根目录创建 `traffic_monitor.db` 和 `logs/` 目录。

## 功能

### 实时监控
- 按进程聚合的流量列表，**按本周期流量降序**排列，一眼看出谁在吃带宽
- 每行显示：PID、进程名、连接数、本周期接收/发送/合计、配额使用情况
- 选中某个进程，右侧联动显示它的**连接明细**（本地端口 / 远端 IP / 远端端口 / 状态）
- 支持按进程名过滤、暂停自动刷新
- 超配额的进程整行标红

### 历史分析
- 选择任意日期，查看当天的**分时流量柱状图**与**进程流量 Top N 排行**
- 当日总流量、活跃进程数、流量高峰时段汇总
- 当日出现过的**远端地址 Top 10**
- **一键导出 CSV**（UTF-8 BOM 编码，Excel 双击打开不乱码）

### 配额与告警
- 针对单个进程设置流量配额，支持「按天」和「累计」两种统计周期
- 超配额时：状态栏提示 + 进程行标红 + 页签角标计数 + 系统托盘气泡通知
- 告警记录页保留全部历史告警
- 告警有 60 秒静默期，避免同一进程反复刷屏

## 关键设计说明

### 为什么存的是「增量」而不是「累计值」

`psutil.Process.io_counters()` 返回的是进程**启动至今**的累计字节数。若把累计值
直接入库，得到的是单调递增的快照，既不能求和也不能画趋势。因此采集器维护上一次
快照，每次入库的是相邻两次的差值；并用 `create_time` 识别 PID 被系统回收复用的
情况，此时重置基线而不是产生一个巨大的负值或错误跳变。

### 为什么按 PID 聚合

流量是**进程级**属性，而连接是**进程内的多条**。一个进程可能同时有几十条连接，
但它的 I/O 计数器只有一个。因此每个进程每轮只读一次计数器，连接信息单独记录。

### 数据口径的重要局限（务必在报告中说明）

Windows 的 `GetProcessIoCounters`（`io_counters` 的底层实现）返回的读写字节数
**同时包含磁盘 I/O 和网络 I/O**，并非纯网络流量。因此一个正在复制大文件的进程
会被统计出较高的"流量"。

要获得纯网络流量，只能借助以下手段，且**均需要管理员权限**：

- **ETW**（`Microsoft-Windows-Kernel-Network` provider）：Windows 资源监视器
  采用的方式
- **TCP ESTATS**（`GetPerTcpConnectionEStats`）：可拿到逐连接的精确字节数
- **WinDivert / Npcap**：驱动层抓包，按进程归属统计，可覆盖 UDP

本项目在架构上把采集逻辑集中在 `core/collector.py`，若要替换为上述精确方案，
只需替换该模块的 `collect()` 实现，其余各层无需改动。

### 其他

- **采集进程范围**：只有当前存在活跃网络连接的进程会被统计。一个进程关闭全部
  连接后即停止计入。
- **「活跃连接」的口径**：只统计**有对端**的连接（即真正的端口映射关系）。
  只监听、未与任何对端通信的本地绑定不计入——一方面它们谈不上映射关系，
  另一方面 Windows 上 IPv4/IPv6 双栈套接字和多网卡 UDP 绑定会让同一个服务
  重复出现十几条（如 `0.0.0.0:5353` 与 `[::]:5353`）。这些本地端口仍然
  保留在进程数据的 `local_ports` 字段里，鼠标悬停在「活跃连接」列即可查看。
- **有流量但没有活跃连接**是正常现象：连接传输完就关闭了，而进程的 I/O 计数器
  仍在累计。此时连接明细会给出提示而不是显示空白。
- **排除自身**：采集服务每轮都要写 SQLite，这些写操作会被 io_counters 计入。
  若不排除，监控工具自己会常年霸占流量榜首，掩盖真正占用带宽的进程。
  由 `collect.exclude_self` 控制，默认开启。
- **数据保留**：默认保留 14 天，服务每 6 小时自动清理过期数据，避免数据库无限膨胀。
- **连接快照**：连接拓扑变化时才写入，并受最短间隔与心跳间隔双重约束，
  避免浏览器频繁开关标签页时刷爆数据库。

## 配置项

`config.json` 全部字段均有默认值，删掉某项不影响运行。

| 字段 | 默认值 | 说明 |
| --- | --- | --- |
| `server.host` / `server.port` | `127.0.0.1` / `8899` | 服务监听地址 |
| `server.timeout` | `5.0` | 客户端请求超时（秒） |
| `collect.interval` | `3` | 采集周期（秒） |
| `collect.min_delta_bytes` | `1` | 低于该值的增量不写库 |
| `collect.exclude_self` | `true` | 是否把采集服务自身排除在统计外 |
| `collect.conn_snapshot_min_gap` | `30` | 连接快照最短写入间隔（秒） |
| `collect.conn_snapshot_heartbeat` | `900` | 连接不变时的心跳写入间隔（秒） |
| `database.file` | `traffic_monitor.db` | 数据库文件 |
| `database.retention_days` | `14` | 历史数据保留天数 |
| `quota.alert_cooldown` | `60` | 同一进程告警静默期（秒） |
| `quota.alert_action` | `alert` | `alert`=仅告警；`suspend`=告警并挂起超配额进程 |
| `log.level` / `log.dir` | `INFO` / `logs` | 日志级别与目录 |

> `alert_action` 默认为 `alert`（仅告警，不干预用户进程）。若需要真正的"控制"
> 动作，改成 `suspend` 即可让超配额进程被自动挂起。
